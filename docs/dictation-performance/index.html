From speech to paste

With the default shortcut, pressing Right Option starts recording. Nemo opens the microphone and buffers speech locally. Pressing Stop closes the recording. The worker then sends the complete audio to the MLX helper on your Mac. The helper joins the predicted tokens into a string. Nemo formats the text, copies it to the clipboard and, if enabled, sends Paste to the active app.

Keep the weights in memory. Wake the GPU while you speak.

The running helper occupies about 27 GB. Starting it and loading the model took about three seconds in the final trials. The M5 Max profile starts loading in the background at launch and keeps the weights until you quit. You can start recording while it loads. A second change addresses the slower first GPU request after a quiet interval.

Why two seconds? With a five-second test recording, the following requests took 222, 227, 406 and 412 ms at one-, two-, three- and four-second spacing. Two seconds was the longest tested interval within 3% of one second. These measurements cover request latency. A separate test of the native nemo-speech backend found no repeatable benefit from recording-time wakeups.

Give the encoder the samples it expects

The frozen test audio was already at 16 kHz, so it skipped a step Nemo performs on this MacBook’s 48 kHz microphone input. Replaying the same recording in microphone format exposed that cost. To reach 16 kHz, Nemo filters out frequencies the lower rate cannot represent, then keeps one sample for every three.

The draft guesses. The target chooses.

Ordinarily the full decoder predicts one token at a time. A token can be a word, part of a word or punctuation. Nemo uses a smaller, faster decoder to propose up to eight tokens before calling the full model again. The full target model checks them together and accepts the matching prefix.

Read less memory for each guess

The draft used to score every possible next token with a weight table of about 705 MB. Repeating that read for dozens of guesses was expensive. Nemo now uses a compact copy to find likely candidates first.

Let the GPU keep its guesses until the batch is ready

Reading a token ID back into Python makes the CPU wait for the GPU. The next guess needs the previous token, but the GPU can feed that token into the next step itself.

Draft loop · Readback comparison

Give Metal the target layers in groups

MLX can build a chain of operations before submitting it to the GPU. During verification Nemo submits each completed group of twelve layers. The GPU can start that group while the CPU prepares the next one.

Target layer traversal · Scheduling profile

Compute the draft output only where it is used

After reading the prompt or repairing a verified batch, the draft must remember every position. Only the last position supplies the next guess. Nemo can keep the entire attention history while skipping earlier expert outputs.

The same recording returned sooner in every pair

We compared a copy of the app installed at the start of the experiment with the optimized build. Each transcribed the same saved 48 kHz WAV twice. We timed the second request on AC power, alternated which build went first, and repeated the six-pair experiment independently.

What “same accuracy” meant here. Exact text, including case and punctuation, matched on 12 frozen recordings and five noise, volume, echo or padding variants. The 87-word project update had zero word errors. Both builds still made 506 word errors against the 499-word reference on the 200-second stress clip.

The prototype that originally measured 585 ms took 603 ms on a later rerun. The final decoder took 563 ms in that same comparison and won all six pairs. The installed build later returned the exact project update in a single 546 ms warm check. Each earlier experiment has its own baseline, so its savings cannot be added to these trials.

Which apparent shortcuts held up?

We tried longer drafts, alternative arithmetic and different GPU settings. A change could win a short test by moving work into startup or by changing the words. These experiments show why we checked the whole signed app against identical recordings.

Profile the target verifier first

In seven warm profiles of the earlier full-vocabulary decoder, verification was the largest stage of a 698 ms request. Drafting came second. These measurements explain where the session started. Repeat the breakdown on the installed decoder before choosing a change.

  1. Longer dictations Time the installed verifier and its expert projections where the code already waits for tokens. Inserting a wait after each GPU operation changes the schedule being measured. Another 5% on a 555 ms request means saving about 28 ms. The target vocabulary projection took 16.5 ms in the earlier profile, which makes the larger expert computations a better first lead.
  2. After a pause Compare the first short request after a real idle interval with an immediate repeat. A cold GPU, model reload or first-use import calls for a different fix than slow token generation.
  3. When the app still feels slow Read finalization, queueing, request and paste-dispatch timings from ordinary dictation. Recipient insertion has its own clock. Use the frozen files to check decoder changes against exact text.
